# w4: lecture notes, homework review and exam questions

## What this week covered

This week walked all of
[gloss3](https://txt.github.io/seai26f/gloss3.html) (clustering by
poles) and the first part of
[gloss4](https://txt.github.io/seai26f/gloss4.html) (how settled a
column is about y). Trees and fast cuts got a light first pass
only, so these notes stay light there too. We will come back to
them next week.

**N1. Labels cost money, x columns do not.** Before anyone pays
for a single y value, the x columns are already on the table. So
we group rows by x distance and let structure show up on its own.
Rows that sit together tend to behave together. That is the whole
reason to cluster before we learn.

**N2. Fastmap in two sweeps.** Finding the two rows that are
furthest apart the honest way means comparing every row with
every other row. Fastmap cheats. Pick any row at random and find
the row furthest from it. That is the first pole. Then find the
row furthest from the first pole. That is the second pole. Two
passes over the data and we hold a line that is roughly the
longest one through the cloud.

**N3. Two labels per split, and no more.** Once the poles are
found, one comparison sorts them by disty so that lo is always
the pole nearer heaven. That line reads the goals of exactly two
rows. Every other row in the split is only ever measured with
distx. Keep that number in mind. It is the seed of active
learning, where every label has a price.

**N4. Projection is high school geometry.** With a as the gap
from lo to a row, b as the gap from hi to that row and c as the
gap between the poles, the row lands at
x = (a² + c² - b²) / (2c) on the line between them. A value near
0 means the row sits with the good pole. A value near c means it
sits with the bad pole. A value below 0 or above c means the row
lies outside the two poles, which fastmap is happy to allow
because its poles are only roughly the furthest pair.

**N5. poles returns a function.** poles does not hand back a
number. It hands back a closure that remembers lo, hi and c. That
closure is exactly the shape keysort wants as a key, and since
each key call costs two distx calls, this is the slow key case
from last week's DSU notes. Each projection is worked out once.

**N6. A sample is enough.** halve finds its poles in a random
sample of the.few rows (128 by default), not in every row. Early
versions used all the rows and paid a full distance sweep at
every split of every level. Then someone tried a small sample and
the splits were just as good. Two far apart rows in a random 128
are already close to the width of the whole cloud, and a split
only needs poles that are far apart and roughly opposed. It does
not need the perfect pair. The moral will come back all semester:
before you speed up a computation, ask how little of the data it
really needs.

**N7. Node is halve, again and again.** Node splits the rows,
then splits each half, and stops when a node holds fewer than
2 * the.stop rows. There are no centroids, no k and no distance
matrix. To place a new row we walk down the tree and at each
level step toward whichever pole is nearer. That costs a
logarithmic number of distance checks.

**N8. sway is where this is heading.** Not examinable. Split the
data, throw away the worse half and keep going only in the better
half. Each level costs two labels, so reaching a good leaf costs
about 2·log(n) labels. That simple baseline turned out to be hard
to beat against much fancier optimizers.

**N9. How settled is a column?** gloss4 asks one question of
every summary: how much does y still wriggle here? A Num answers
with its standard deviation. A Sym answers with its entropy. Both
read 0 when the column has made up its mind and grow as it
spreads out. Since both answer the same div call, the tree code
never has to ask which kind of column it holds.

**N10. Entropy as twenty questions.** Entropy is the average
number of yes or no questions you need to find one symbol in a
bag. A symbol that fills a share p of the bag takes log2(1/p)
questions to corner, and you go looking for it with probability
p. Averaging gives e = ∑ p·log2(1/p) = -∑ p·log2(p). Some checks
worth doing by hand:

| bag       | entropy   | why                                  |
|-----------|-----------|--------------------------------------|
| {a,a,a,a} | 0 bits    | nothing to ask                       |
| {a,b}     | 1 bit     | one question                         |
| {a,b,c,d} | 2 bits    | two questions                        |
| {a,a,a,b} | ≈0.81 bits | you mostly hunt the easy symbol     |

A skewed bag is cheaper than a fair one, which is why entropy
falls as a column settles.

**N11. Expected value, and val.** If you split n rows into sides
of size na and nb, a random row lands on side a with probability
na/n. So the diversity a random row lives with after the split is
(diva·na + divb·nb) / n. That one number is val. Lower is better.
It does not care whether y is a number or a symbol.

**N12. Trees and cuts, lightly.** A cut is one test on one x
column: x ≤ v for numbers and x == v for symbols. A tree takes
the best cut, splits the rows and recurses on each side. Two
ideas made it into class. First, least is a small closure that
remembers the best cut seen so far, so we never build a list of
all the candidates. Second, scoring every cut the obvious way is
O(n²), but if we sort once and grow a left summary one row at a
time, the right summary is just tot - here. That is the pool
algebra from week 1 paying off, and it scores every cut in one
pass. More on both next week.

## Errata: the entropy formula

In class the entropy formula was likely written as
∑ -p·log(1/p). That has the sign wrong. Since p is at most 1,
log(1/p) is never negative, so that sum is zero or negative, and
a fair coin would come out as -1 bit. The correct forms are

```
e = -∑ p·log2(p)      -- minus sign, log of p
  =  ∑ p·log2(1/p)    -- no minus sign, log of 1/p
```

Pick one form and keep the minus sign or the 1/p, never both.
Also note the base: the Lua code divides by log(2) to get bits.
The same slip turns up as an exam bug below (Q6).

**What usually lands below the line.** keysort is sorted(key=),
some is random.sample, slice is list slicing and floor is
integer division or math.floor. What stays above the line is
poles, halve, Node and the leaf walk.

**Check question 1 (the.few).** Rerunning --half with --few=8 and
--few=512 changes the halves only a little. With 8 rows the poles
wobble more from seed to seed. With 512 you are sampling all 398
rows anyway. The halves hardly move because any far apart pair
from a random sample is already near the width of the data, and
the split only needs roughly opposed poles.

**Check question 2 (labels versus distances).** Each halve reads
the goals of two rows, the two poles. Every row in the node gets
distx'd (twice, in fact, once per pole), plus the two far sweeps
over the sample. When a label costs money, two labels per split
is what makes this approach affordable.

**Check question 3 (leaf count).** With 398 rows and stop=32 a
node splits only if it has at least 64 rows. So 398 splits into
199 and 199. Each 199 splits into 99 and 100. Each of those
splits into halves of 49 or 50, and all of those are under 64.
That gives three levels and 8 leafs. Predict first, then run.

**Check question 4 (the triangle).** Drop a perpendicular from
the row to the line and call its height h and its foot x. Then
a² = x² + h² and b² = (c - x)² + h². Subtract the second from the
first to lose h: a² - b² = 2cx - c². Solve for x and you get
x = (a² + c² - b²) / (2c). A negative x means the row sits past
lo, on the side away from hi.

# Programming notes: the champion closure and the one pass cut

A short tour, kept light since we only touched it in class.

**1. Keep the best, not the list.** least returns a closure that
holds one thing, the best candidate so far. Offer it a candidate
by calling it with one. Read the winner by calling it with
nothing.

```lua
function least(    lo)
  return function(x)
    if x and (lo == nil or x[1] < lo[1]) then lo = x end
    return lo end end

best = least()
best{0.9, "a"}; best{0.4, "b"}; best{0.7, "c"}
print(best()[2])   --> b
```

Memory stays constant no matter how many candidates go past.

**2. The slow way to score cuts.** For every cut, build a left
summary and a right summary from scratch. That is n rows per cut
and about n cuts, so O(n²).

**3. The one pass way.** Sort the (x, y) pairs once. Walk left to
right adding each y to a growing left summary. The right summary
is never built. It is the total minus the left, which Num gives
us in O(1) because week 1 made summaries subtract.

```lua
here = acc()
for j,p in ipairs(xy) do
  here:add(p[2])
  if j < #xy and p[1] ~= xy[j+1][1] and big(j, #xy) then
    best{val(here, tot - here), c.at, p[1]} end end
```

The two guards matter. Cuts only fall between different x
values, and big refuses any cut that leaves fewer than the.leaf
rows on a side.

**The rule.** Sort once, add as you go and subtract to get the
other side. Then remember that the rows you feed in can be a
sample too, just like the poles.

**Q6. Negative surprise**

```lua
function SYM.div(i)

**Q7. The unweighted average**

a) Why is val an expected value?

b) What kind of cut does this version reward unfairly, and what

```

a) Why can the right hand summary be written as tot - here?

## Answers

**A1.** Pick a random row and find its furthest row (pole one),
then find the row furthest from pole one (pole two). With the
change, both poles are the far point of two unrelated random
rows. They can be close to each other or even the same row. If
they are the same row then c is just TINY, the projection divides
by almost zero and the split order becomes noise. The second
sweep must start from the first pole.

**A2.** Two labels, one for each pole. Without the swap, lo is
the better pole only by luck, so the demo's check that
disty(a) <= disty(b) fails about half the time depending on the
seed. The tree loses its promise that the first half leans
toward heaven, which is exactly what sway needs.

**A3.** x = (a² + c² - b²) / (2c). Below 0 means the row lies
beyond lo, away from hi. With the bug the code divides by 2 and
then multiplies by c, so every value is scaled by c². Since c is
the same for every row, the sort order does not change and the
halves are identical. Nobody notices until someone reads the
number as a position between 0 and c.

**A4.** Sorting by projection lines rows up along the pole to
pole axis, and the median gives two halves of equal size. With
the bug the middle row lands in both halves, so #lo + #hi is one
more than #rows and the rows conserved assert fails.

**A5.** Eight (see homework check question 3). With the bug a
node splits at 32 rows or more, so the 49 and 50 row nodes split
again and we get 16 leafs of about 25 rows. The rows conserved
and leafs > 1 asserts still pass. The trouble is that leafs are
now smaller than the chosen stop size, and small leafs start to
memorize rather than summarize.

**A6.** Entropy is the average number of yes or no questions to
find a symbol, about 0.81 bits for {a,a,a,b}. The bug keeps the
minus sign and also uses log(1/p), so a fair coin scores -1 bit.
Every div is now zero or negative, and the most mixed sides score
lowest. Since lower val is better, the tree now prefers the worst
cuts. This is the errata slip in code form.

**A7.** A random row lands on each side with probability equal
to that side's share of the rows, so weighting each div by size
gives the expected diversity. Without weights, a cut that peels
off a tiny pure side (div of 0) gets half its score for free. The
big guard partly saves us by refusing sides smaller than
the.leaf.

**A8.** Summaries subtract in O(1), so the right side is the
whole minus what we have already added. Without the distinct
check, a cut can be scored between two rows that share the same
x. The score counts one of them on the left and one on the
right, but the real test x ≤ v sends both to the left. The tree
then picks cuts using scores for splits it can never make.
