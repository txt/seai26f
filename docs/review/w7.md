# w7: lecture notes + exam questions

First half: more uses for trees (monitors, test partitions,
feature selection), the labeling problem, holdout hygiene, and
explore vs exploit. Second half: three student talks on
multi-objective optimizers (GALE, IBEA, MOEA/D). The project
also changed (see N8).

**N1. Trees give monitors, too.** Last week a tree gave a plan:
the tests on the path from your leaf to a *better* leaf. Run
the same walk to a *worse* leaf and you get a monitor: the
tests you must NOT cross. In class (students as tree nodes),
our row sat in the second-best leaf; the worst leaf was one
flip away (`age > 7` vs `age <= 7`). So watch `age`: if it
drifts across 7, raise an alarm. Plans and monitors are the
same code. For a gentle plan, pick the better leaf that needs
the fewest flips, not always the best leaf.

**N2. One tree, many jobs.** Classification and regression use
the same tree and the same `leaf` lookup; only the leaf summary
differs (mode of a symbol, or mean of a number). For testing:
run a tree over a program's trace logs, and each branch is one
distinct behavior, so one test per leaf gives a varied test
suite. Cluster the inputs and the outputs separately and you
can ask a bolder question: can a map from input clusters to
output clusters stand in for the program in between?

**N3. Small trees select features.** Label 50 rows with a leaf
of 3 and the tree has at most ~16 leaves, so ~15 tests, so at
most ~15 attributes, even if the data has 1,000. Across 127
MOOT data sets, the trees used single-digit attributes, and
performance did NOT fall as the number of x columns rose. Noisy
and useless columns are just never picked. At NASA this meant
the "one slide" rule: managers had ~17 minutes per meeting, so
a 10-20 node tree, read as plans, was the whole briefing.
Binary splits keep each child big; a wide fan-out starves the
subtrees. Odd corollary: three collinear "killer" variables?
Keep one. The others add no new information. Old rule of thumb:
about √N columns and N/10 rows carry the signal.

**N4. X is cheap, Y is costly.** Data is everywhere; *labelled*
data is not. Was this GitHub project a success? (Interview the
team.) What mpg does this 15-year-old used car get? (Drive it.)
Was NC State a good choice? (Ask in two years.) SQLite's build
options give ~3 billion builds; each label means a build plus a
full test run. Some labels are secret: two contractors in the
same building would not share effort data. So do as much as
possible with x alone. Two cheap labeling policies: (a) cluster
on x, label one centroid per cluster; (b) far-first: label a
row, then the row farthest from all labelled rows, and repeat,
so the labels spread over the space. A *passive* learner takes
every row it is given; an *active* learner asks "given my model
so far, what next?" and so skips noisy and redundant rows. How
many labels you need depends on the data: `1,1,1,...` needs
one; `9,7,12,16,23,...` needs many.

**N5. Holdout hygiene.** Shuffle first, for two reasons: (1) 20
repeats need 20 different splits; (2) order effects (a hospital
dump may list babies before adults, or one clinic before
another). Keep train and test apart: a model scored on its own
training rows describes the past, not the future. Many
optimization papers report results on the rows the search saw;
ezr loses some points by scoring on the holdout, on purpose.
Why no 60/20/20 validation split here? With ~50 labels, a third
split leaves almost nothing. The budget/check heatmap came from
100,000 random runs in two hours on a laptop: an experiment no
LLM-based method could afford. Hyperparameter optimization
searches the "magic" settings: `leaf`, the label budget, the
distance exponent `p` (1 = Manhattan, 2 = Euclidean).

**N6. Explore vs exploit.** Score each candidate with P(best)
and P(rest). *Exploit*: sample where P(best) is high and P(rest)
is low. *Explore*: sample where P(best) ≈ P(rest), the zone of
most confusion. To learn the US/Canada border, go to Detroit;
once you know, go to Miami or Yellowknife. Doctors do the same:
early tests aim to cut the space of diagnoses. The canon: early
estimates are noise, so explore first, then decay towards
exploit. timm's warning: he lost 2.5 years (and 8 students)
tuning decay rates; across 20 seeds the "best" decay was noise.
Now sway3/`acquire` is greedy, exploiting from day one (with
the 0.66 cull as a hedge). No free lunch (Wolpert): no learner
or optimizer is best on all data, just as some input order
breaks quicksort. So you must experiment.

**N7. Three optimizers from the talks.** The baseline: NSGA-II
or SPEA2, ~100 individuals × ~100 generations, up to 10⁴ model
calls. *Binary domination* (gloss6) is their selector, and in
many-objective spaces it fails: nearly every row is
non-dominated, so selection pressure vanishes.
- **GALE** (geometric active learner): fastmap splits the
  population; label only the two poles; if one pole dominates,
  drop the half near the loser; recurse; then nudge survivors
  toward the better pole (directed mutation). ~2·log2(N)
  labels per generation: 25-100× fewer evaluations than NSGA-II
  (CDA: hours down to ~4 minutes). Lesson from POM3: NSGA-II
  "cut cost" by finishing fewer requirements, so the best
  number was not the best plan. Back-story: a student broke
  GALE's mutator by accident, and it still worked. That led to
  sway, and to this course.
- **IBEA**: continuous domination. Additive ε-indicator
  I(a,b) = maxᵢ (fᵢ(a) − fᵢ(b)) (minimize): how far a must shift
  to be no worse than b. Fitness(x) = Σ over other y of
  −exp(−I(y,x)/(c·κ)). Drop the least fit row, recompute,
  repeat. On a 290-feature product line (2²⁹⁰ configs), many
  objectives: IBEA found far more valid configs than NSGA-II.
- **MOEA/D**: decompose into many single-goal subproblems, one
  weight vector λ each. Tchebycheff score
  g(x|λ,z) = maxᵢ λᵢ·|fᵢ(x) − zᵢ|, z = best value seen per goal.
  Neighbors (similar λ) breed and share children. Evenly spread
  λs give a spread front. Needs normalized goals: raw cost in
  the thousands swamped coverage in 0..1.
- Metrics: *hypervolume* (space dominated, from a reference
  point; bigger is better; depends on that point), *spread*
  (evenness along the front). timm: the Pareto frontier is an
  idea from the 1890s; recent results say most good answers sit
  in one narrow zone, so zoom, do not map the whole front.

**N8. The new project.** Tim's hypothesis: neuro-symbolic
tools improve when the symbolic half is factored into small
reusable parts, so skill i+1 costs less code than skill i. Its
rival: refactoring is waste; each skill costs the same. Task:
pick a MOOT data set, have an LLM write ~20 business goals for
it, then build them 7 ways: {raw Python, scikit-learn, ezr} ×
{reuse earlier skills, or not}, plus one by hand. Six of the
seven need no coding, only prompts. Reset the LLM between trials
(fresh directory; delete any private skills file it wrote). The
"normal" industry mode is no reuse plus a big library. Compare
the results with `same` and `ranks` (gloss6). Undergrads: one
domain, 3 pages. Grads (optional switch): three domains, 6-9
pages. A full run takes 3-4 hours, so start early.

## Exam questions

**Q1. Plans and monitors**

a) A tree can give a plan and a monitor. Say how each is read
from the tree, and how they differ.

b) Your row has `age` 9, `load` 4, `size` 5 (lower `d2h` is
better). Give the best plan, the smallest-change plan that still
improves, and the one test to monitor.

```
age <= 7
|  size <= 3 .......... d2h 0.2  ▲
|  size >  3 .......... d2h 0.4
age >  7
|  load <= 5 .......... d2h 0.5
|  load >  5 .......... d2h 0.8  ▼
```

**Q2. Small trees, big tables**

a) You grow a binary tree from 50 labelled rows with a minimum
leaf of 3. The data has 1,000 x columns. At most how many
columns can the tree test? What did the 127-data-set MOOT study
find about performance as the column count grew?

b) Three columns each predict the goal almost perfectly, and
they are collinear. Why keep only one before tree learning?

**Q3. The labeling problem**

a) Give two SE examples where x is cheap and y is costly, and
say what makes each y costly.

b) Describe two label-selection policies that use only x, and
say why each beats picking 50 rows at random.

**Q4. Holdout hygiene**

a) Give two reasons to shuffle rows before a train/test split.

b) Many optimization papers report the quality of the final
answer on the same rows the search used. What is wrong with
that, and why does ezr skip a validation set?

**Q5. Explore vs exploit**

a) With P(best) and P(rest) per candidate, where does an
exploiter sample, and where does an explorer sample?

b) The textbook says explore first, then exploit. Give the
argument for it, and timm's evidence against tuning that
schedule.

**Q6. GALE**

a) List GALE's three ideas, one sentence each.

b) A population of 128. Roughly how many model calls does
GALE's recursive split spend per generation, against NSGA-II?
What does the POM3 result warn about trusting "better scores"?

**Q7. Many objectives**

a) Why does binary domination lose selection pressure as the
number of objectives grows?

b) Minimize both goals. a = (0.2, 0.6), b = (0.4, 0.3). Compute
the additive ε-indicator I(a,b) and I(b,a). Then, with ideal
z = (0, 0), compute the Tchebycheff score of each for
λ = (0.5, 0.5) and λ = (0.9, 0.1). Which row wins under each λ?

**Q8. The project**

a) State Tim's hypothesis and its rival. How many treatments
are there, and what are they?

b) Why must the LLM be reset between trials, and how do you
decide whether "ezr + reuse" beat "scikit-learn, no reuse"?

## Answers

*A practice bank. These are not the exam.*

**A1.** Plan: walk from your leaf up to the shared ancestor and
down to a better leaf; the tests you cross are the changes to
make. Monitor: the same walk to a worse leaf; those tests are
the drifts to watch. For (b): the row lands at `d2h` 0.5. Best
plan: `age <= 7` and `size <= 3` (two changes, 0.2). Smallest
change: `age <= 7` only; `size` 5 already sends it to 0.4. Watch
`load`: above 5, the row falls to 0.8.

**A2.** 50/3 gives at most ~16 leaves, so ~15 tests, so at most
~15 columns of 1,000. MOOT trees used single-digit columns, and
performance stayed flat as columns grew: no sign that ignoring
more columns hurt. For (b): one killer cut already splits the
rows. The other two carry the same signal, so they add nothing;
they only take cuts and rows that a new signal could use deeper
down.

**A3.** Examples: project success (needs interviews, months
later); build configs (each needs a build plus a full test run;
SQLite has ~3 billion); used-car mpg (needs a drive); effort
data (may be secret). Policies: cluster on x and label each
centroid (one label stands for many similar rows); far-first
(each new label goes where nothing is labelled yet). Random
picks fall into dense clumps and buy near-duplicate labels.

**A4.** Twenty repeats need twenty different splits; and data
files often have an order (by age, sex, clinic) that biases a
split. Scoring on search rows is optimistic: it reports how well
you fit what you saw, not how well it transfers. ezr has ~50
labels; a 60/20/20 split would leave about ten rows per part.

**A5.** Exploit: high P(best), low P(rest). Explore: where
P(best) ≈ P(rest), the zone of most confusion. For: early
estimates rest on few labels, so trusting them is risky; probe
the boundary first (Detroit before Miami). Against: tuned decay
rates gave no stable winner across 20 seeds (noise), so ezr
exploits greedily from the start, with a gentle 0.66 cull.

**A6.** Spectral split (fastmap poles), active labels (only the
poles; prune the half near a dominated pole), directed mutation
(push toward the better pole). About 2·log2(128) = 14 calls per
generation, vs 128 for NSGA-II. POM3: NSGA-II's cheaper plans
were cheaper because teams finished less work. A better number
can hide a worse plan; check what the plan does.

**A7.** With many goals, a random pair is almost always better
on one goal and worse on another, so few rows dominate any
others; nearly all rows rank equal and selection is a coin
toss. I(a,b) = max(−0.2, 0.3) = 0.3; I(b,a) = max(0.2, −0.3)
= 0.2. Tchebycheff, λ = (0.5, 0.5): a = max(0.10, 0.30) = 0.30,
b = max(0.20, 0.15) = 0.20, so b wins. λ = (0.9, 0.1):
a = max(0.18, 0.06) = 0.18, b = max(0.36, 0.03) = 0.36, so a
wins. Different weights pick different rows: that is how MOEA/D
covers the front.

**A8.** Hypothesis: factor the symbolic half into small reusable
parts and each new skill costs less code. Rival: each skill costs
the same, reuse or not. Seven treatments: {raw Python,
scikit-learn, ezr} × {reuse, no reuse} = 6 LLM runs, plus 1
manual. Reset because LLM tools cache notes and skills files;
without a reset, trial 4 learns from trial 3 and the repeats are
not independent. Collect a score per trial for each treatment,
call `same` (Cohen, Cliff's δ, KS must all agree); claim a win
only if they are not `same`, or read it from `ranks`.
